## If the worker restarts before the migrations are applied

**Do not let that happen now.** The send handler selects `Message.mailboxId` and `sendClaimedAt`.
Once the new code is loaded, every send and every sequence advance would fail on the missing
columns until `migrate deploy` runs. Apply the migrations first (step 3), then restart the worker.
The paragraphs below were written for the ledger migration alone.


This is safe while fallback is off. With `enabled: false`, `providersFor` returns before any query
touches `ProviderCall`, and the stages behave as before. What does change:

- **Contacts stage.** When fallback is off, it records "skipped" with the same "Contact providers are off" reason as before.
- **Find emails.** A run now counts an address found by the contacts stage as a result (the D03 fix).

Do not switch fallback on until the migration is applied. Every provider call writes a ledger row
first, so an unmigrated database would fail each attempt as a transient error, and nothing would be
spent.

## Rollout, in order

1. **Take a fresh backup.** Keep it outside the repository.
   ```bash
   pg_dump -Fc -d signalroom_dev -f "../signalroom-backups/signalroom_dev-$(date +%Y%m%d-%H%M).dump"
   ```
2. **Run the release checks** on the isolated test database:
   - `npm run typecheck && npm run lint && npm run test`
   - `SIGNALROOM_BUILD_DIR=.next-verify npm run build`
   - `npm run e2e`

   None of these touch `signalroom_dev`.
3. **Apply the migrations.** They are additive and need no downtime.
   ```bash
   npx prisma migrate deploy
   ```
   Confirm with `npx prisma migrate status`, which should report "Database schema is up to date".
4. **Build into a new directory**, so the running app is not disturbed: `SIGNALROOM_BUILD_DIR=.next-release npm run build`. Then stop the app, swap `.next-release` into `.next`, and start the app. Or stop the app, run `npm run build`, and start it. Either way there is a short outage, and it is the operator's choice.
5. **Restart the worker** with `npm run worker`, so it loads the same revision as the app.
6. **Smoke test with free calls only**:
   ```bash
   npm run smoke:providers -- --workspace <slug>
   ```
   This makes token checks and free calls, and spends no credits. Record the table it prints.
7. **Enable fallback on purpose.** In Settings → Lead Sources & APIs → Apify enrichment, choose the steps and the caps, then run one opportunity with "Enrich opportunity". Read the "Providers for this step" list on each stage.
8. **Optional: a paid smoke test**, only with spending authorisation, against a domain you are allowed to test:
   ```bash
   npm run smoke:providers -- --workspace <slug> --paid --max 3 --domain <d> --first <f> --last <l>
   ```

## Rollback

- **Code:** redeploy the previous build and revision, then restart the app and the worker.
- **Database:** leave the new tables and columns in place. Older code ignores them, and dropping `ProviderCall`, `BillingEvent` or `BillingCheckout` would destroy the record of what was spent or paid. Because `imapHost` and `imapUser` became optional, older code would fail on a Gmail, Microsoft or send-only mailbox. Disconnect those mailboxes before rolling code back.
- **Fallback:** switch it off in Settings. It takes effect on the next stage, and nothing already saved is removed.
- **Data written by fallback:** people, addresses and company fields carry their source, such as `hunter:email-finder`, `signalhire:search` or `apollo:people-enrichment`, together with the run id, so they can be reviewed or recycled per run. Do not bulk-delete them with SQL; use the recycle bin.

## New server configuration (all optional; each feature says so on screen when unset)

| Variable | Enables |
| --- | --- |
| `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` | Gmail mailboxes, with the Gmail API enabled and the redirect `/api/mailboxes/oauth/gmail/callback` registered. The Google calendar uses the same client, with `/api/calendar/google/callback`. |
| `MICROSOFT_OAUTH_CLIENT_ID`, `MICROSOFT_OAUTH_CLIENT_SECRET`, optional `MICROSOFT_OAUTH_TENANT` | Microsoft 365 mailboxes (Mail.Send, Mail.Read) and calendars (Calendars.ReadWrite). Redirects: `/api/mailboxes/oauth/microsoft/callback` and `/api/calendar/microsoft/callback`. |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` | Browser push. Generate one P-256 pair and never rotate it casually, because every browser subscription is tied to the public key. |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | Plan payments. Start with `rzp_test_` keys. Point the Razorpay webhook (events `payment_link.paid`, `.expired`, `.cancelled`) at `/api/webhooks/inbound/razorpay`. |
| `APP_URL` | Absolute OAuth redirects and the payment return link, when the app sits behind a proxy. |
